# The 23 components you need

**TLDR.** Learn these 23 well and you can design any small-business-plus-spike prompt. They're in the order you use them in the interview. Each card starts with a plain-English explanation. "Also covers" defines the related terms an interviewer might use. Everything else is in the [optional reference](reference.html); skip it for now.

**Study plan**

- **Day 1:** cards 1 to 10. Then draw the pizza-shop V1 from memory.
- **Day 2:** cards 11 to 18. Then answer 2 sample questions out loud.
- **Day 3:** cards 19 to 23 and the numbers. Then 2 more questions and 10 drills.

## Draw these in V1

| # | Part | In plain English | Use it for | Example | Say this | Also covers |
|---|---|---|---|---|---|---|
| 1 | CDN | A network of servers around the world that keep copies of your website's files: pages, images, scripts. Visitors get the files from a server near them instead of from yours. Think of local warehouses stocking your product, so not every order ships from the factory. | Every design. During a spike it soaks up most of the traffic, because most requests are for files that rarely change. | A bike shop's website gets shared on a popular forum, and 50,000 people open the homepage within an hour. Each visit loads the page, 20 product photos and some scripts: about 2 MB. Without a CDN, all of that comes from the shop's two servers, which max out and slow to a crawl. With a CDN, the first visitor in each region triggers one fetch from the shop; everyone after that gets the copy from a CDN server nearby. The shop's servers only see the few requests that actually change something, like adding to cart. **Why:** the files are the same for everyone, so there's no reason to send them from your servers every time. | "The CDN takes most of the read spike before it reaches us." | **DNS:** the internet's phone book, turning pizza.com into a server address. Before a launch, set it to refresh often (a low TTL) so you can redirect traffic quickly. |
| 2 | Load balancer | A traffic cop in front of your servers. You run two or more identical copies of your backend, and it hands each request to one of them. It checks every few seconds that each copy is alive and stops sending traffic to any that don't answer. | Every design. If one copy crashes, users don't notice. | A tire shop's booking site runs two copies of its backend. At 9 AM, one copy crashes on a bug in a rarely used page. Within a few seconds, the load balancer's health check gets no answer from it, so every new request goes to the other copy. Customers keep booking and never notice. When the engineer restarts the crashed copy, it passes the health check and starts getting traffic again. **Why:** with a single copy, that crash would have taken the whole site down. | "Two copies behind a load balancer, so one can die." | **Health check:** that "are you alive?" ping. The load balancer also handles HTTPS encryption. A **reverse proxy** is the same idea. |
| 3 | Stateless API, one service | "Stateless" means a server copy doesn't remember anything about a user between requests. Anything that must be remembered (carts, orders, logins) goes in the database or cache. So any copy can handle your next request, and you get more capacity by starting more copies. If copy A kept your cart in its own memory instead, you'd be stuck with A, and your cart would vanish if A crashed. | Every design. | A pizza shop expects 10x its normal traffic on game day, so an hour before kickoff the engineer goes from 2 copies of the backend to 8. A customer adds a pizza to the cart; copy 1 handles it and saves the cart in the database. Then they pick a pickup time; copy 5 handles that and reads the cart back from the database. Neither copy had to remember anything, so the 6 new copies were useful the moment they started. **Why:** if carts lived in each copy's memory, every customer would be tied to one copy, the new copies would sit idle for existing customers, and a crash would wipe out carts. | "One service, run as several identical copies. They're stateless, so I scale by adding copies." | **Monolith:** one program deployed as a unit, right for a small team. **Microservices:** many small programs calling each other over the network; more moving parts, for big orgs. **Managed containers:** you hand the cloud your packaged app and it runs the copies (Cloud Run, Container Apps, ECS). **Kubernetes:** running your own cluster for that; powerful, but it needs people to operate it. **Serverless functions:** code that runs once per event; fine for small glue. |
| 4 | Postgres (managed) | The standard relational database: tables of rows, like spreadsheets that many people can edit at once without corrupting anything. It's your source of truth: if it says an order is paid, it's paid. Two features matter most. Transactions: several changes succeed or fail together. Constraints: rules the database enforces itself, like "no two orders with the same id". "Managed" means the cloud handles backups, patches and recovery. | Orders, payments, stock, bookings: anything that must be correct. | A customer books the 9 AM Saturday slot at the tire shop. Two things must happen together: mark the bay as taken, and save the booking with their phone number. Postgres does both in one transaction, or neither if anything fails halfway, say the server crashes in between. A uniqueness rule on (bay, time) means the database itself rejects a second booking for the same bay and time, even if two customers click at the same instant. **Why:** these are exactly the facts that must never be wrong, and Postgres guarantees them for you. At a few bookings a second, one database has huge room to spare. | "Postgres, not DynamoDB: my write changes two rows together, and at these numbers one database is plenty." | **ACID transaction:** "reserve the pizza" and "create the order" either both happen or neither does. **Index:** a sorted lookup, like a book's index, so a query finds a row without reading every row; every frequent query needs one. **DynamoDB:** Amazon's database built for huge scale on simple "get by id" lookups, but multi-row changes are clunkier, and one very popular item tops out around 1,000 writes/s. **Sharding:** splitting data across several databases; only when one can't keep up, never in V1. |
| 5 | Object storage | Cloud storage for files (photos, PDFs, videos), each saved under a name. Like Google Drive for your app: cheap and practically unlimited. Databases are bad at holding big files, so you keep the file here and just its name in the database. | Anything bigger than a row of data. | A print shop lets customers upload 10 photos, about 4 MB each, for holiday cards. The browser asks the API for upload links, gets back 10 signed URLs, and sends each photo straight to object storage. The database stores only each file's name next to the order. Later, a print worker downloads the photos from storage to build the print file. **Why:** 40 MB per order times thousands of orders would clog the API servers and bloat the database. Storage is built for exactly this, cheaply. | "The browser uploads straight to storage with a signed URL, so photos never pass through our servers." | **Signed URL:** a temporary link that lets one user upload or download one file directly. Serve the files through the CDN. |
| 6 | Queue + workers | A to-do list for slow work. Say a customer orders: instead of making them wait while you send a confirmation text, the server writes a note ("text this number") on the queue and replies right away. Background programs called workers pick notes off the list and do the work. In a spike, notes just wait their turn; nothing is lost. | Emails, texts, image processing: anything that can lag a bit. | When a pizza order is paid, the shop texts a confirmation. The SMS provider takes 1 to 2 seconds and sometimes times out. Instead of making the customer wait, the API puts "text +1 555 0100: order 42 confirmed" on the queue and shows the confirmation page right away. A worker picks up the note and sends the text. On game day, 900 orders arrive in 30 minutes; texts fall a few minutes behind, but none are lost. If the provider fails, the worker retries; after 5 failures the note moves to the dead-letter queue and someone gets an alert. **Why:** checkout stays fast, and a slow text provider can't break ordering. | "At-least-once delivery, plus workers that are safe to run twice." The queue may occasionally hand out the same note twice, so doing a job twice must be harmless. | **Dead-letter queue:** where a note goes after failing N times, so one bad job doesn't block the rest; alert on it. Add workers when the list gets long. **Kafka:** an event log many programs can read and re-read; overkill for a to-do list. **Pub/sub:** one message delivered to several listeners. **Outbox:** save the message in the same transaction as the order, so you can't save one and lose the other. |
| 7 | Sweeper and reconciliation jobs | Small programs that run on a timer (every minute, every night) to clean up. A sweeper finds things that got stuck, like a pizza someone reserved but never paid for, and releases them. A reconciliation job compares your records with an outside source, like Stripe's list of payments, and fixes mismatches. They catch whatever slipped through: crashed requests, lost messages. | Expired holds, stuck orders, matching payments. | At the pizza shop, 50 people reserve pizzas and then abandon the Stripe payment page. Their holds expire after 10 minutes. Every minute, the sweeper finds holds past their expiry, asks Stripe "was this one paid?", and if not, puts those pizzas back on sale. Every night, the reconciliation job pulls Stripe's list of the day's payments and compares it with the paid orders. It finds one order whose "paid" webhook never arrived, and marks it paid. **Why:** in any real system some messages get lost. These jobs make sure everything ends up correct anyway. | "Every minute, release expired holds, after asking Stripe whether they were paid." | **Cron:** the classic name for "run this on a schedule". Make sure only one copy runs at a time, so two sweepers don't fight. |

## Protect the invariants

An invariant is a rule that must never break, like "never sell more pizzas than the ovens can make".

| # | Part | In plain English | Use it for | Example | Say this | Also covers |
|---|---|---|---|---|---|---|
| 8 | Conditional update | Do the check and the change as one database command: "subtract 2 from stock, but only if at least 2 are left". The database runs it as a single step, so two buyers can't both see "1 left" and both buy it. If nothing changed, it's sold out. The bug it prevents: code that reads "1 left", then writes "0 left" a moment later; two customers can slip in between those steps and both succeed. | **No oversell** of stock, seats or time slots. | An electronics shop has 1 TV left at the sale price. Alice and Bob click Buy in the same millisecond. Each request runs `UPDATE stock SET left = left - 1 WHERE id = 7 AND left >= 1`. The database runs them one after the other. Alice's changes 1 row, and left becomes 0. Bob's changes 0 rows, because left is no longer at least 1, so Bob sees "sold out". **Why:** if the code first read "1 left" and then wrote "0", both could read 1 before either wrote, and the shop would sell 2 TVs it doesn't have. | "One statement, so the database refuses to go below zero." | **SELECT ... FOR UPDATE:** lock the row while you run more complicated logic; others wait their turn. Avoid keeping the count in Redis or using a "distributed lock": then two places hold the truth, and they can disagree. |
| 9 | Holds that expire | Like a store setting an item aside for 10 minutes while you get your wallet. When checkout starts, you reserve the item first (a hold), then take payment. If they pay, the hold becomes a sale. If 10 minutes pass without payment, the sweeper (card 7) puts it back on sale. Each order's status only moves forward: held, then paid or expired. | Anything reserved before it's paid for. | A customer picks 2 pizzas for the 6:00 pickup slot and clicks checkout. The shop immediately reserves 2 of that slot's 150 pizzas, marks the order held with a 10-minute expiry, and sends the customer to Stripe. If they pay, Stripe's webhook flips the order to paid and it goes to the kitchen. If they wander off, after 10 minutes the sweeper releases the 2 pizzas for someone else. **Why:** if you charged first and then found the slot full, you'd owe refunds and have angry customers. Holding first means you only take money for pizza you can actually make. | "Hold, then charge, so we never take money for something we can't deliver." | **State machine:** the fixed list of statuses and the allowed moves between them. Because status only moves forward, a late or repeated message from Stripe can't turn a paid order back into a held one. |
| 10 | Idempotency key | "Idempotent" means doing something twice has the same effect as doing it once. Networks are flaky: a customer double-taps "Pay", or their phone retries after a timeout. So the app attaches a random id to each user action, one per tap of "Place order". The server saves it with a rule that ids must be unique. If the same id arrives again, the server returns the original result instead of creating a second order. | **No double charge.** Every action that creates or charges something, and every webhook. | A customer on a train taps "Place order". The request reaches the server and the order is created, but the reply is lost when the train enters a tunnel. The app automatically retries with the same key, a7f3. The server sees that key already exists and returns the original order instead of creating a second one. The shop also passes the order id to Stripe as Stripe's own idempotency key, so even a repeated charge request is charged once. **Why:** retries are unavoidable on real networks, and without the key, every retry is a possible double charge. | "A client key with a unique constraint, the same key passed to Stripe, and webhook event ids deduped." | **Unique constraint:** the database rule that rejects duplicates. The same trick stops double booking: one booking per bay per time slot. **Webhook dedupe:** Stripe can send the same notice twice, so save its event id and ignore repeats. True "exactly once" isn't achievable; you get "at least once, and repeats are harmless". |

## Survive the spike

| # | Part | In plain English | Use it for | Example | Say this | Also covers |
|---|---|---|---|---|---|---|
| 11 | Cache with a short TTL | A cache is a small, very fast memory holding copies of recent answers, so you don't ask the database every time. Redis is the usual tool. The TTL ("time to live") is how long a copy is kept before it's thrown away and fetched again. With a 2-second TTL, an answer is at most 2 seconds old, and the database sees one query every 2 seconds instead of thousands. | Things everyone reads at once: "slots left", the menu. | On game day, 20,000 people keep refreshing "slots left": about 500 requests a second asking the database the same question. With a 2-second cache, the first request every 2 seconds reads the database and stores the answer in Redis. Everyone else gets the Redis copy in under a millisecond. The database answers 1 query every 2 seconds instead of 1,000. Someone may see "3 left" when it's really 0; at checkout, the conditional update (card 8) says sold out, and the page tells them. **Why:** a 2-second-old count is fine for browsing, and the sale itself is still decided by the database. | "Cached for 2 s. It's a hint; the database is the truth." Never decide a sale from the cache; the conditional update (card 8) decides. | **Invalidation:** deleting copies whenever the data changes; harder than a short TTL. **Stampede:** a popular copy expires and thousands of requests hit the database at once; let one request refresh it while the others get the slightly old copy. **Hot key:** one item everyone reads; also keep a 1-second copy inside each server. |
| 12 | Rate limits | A cap on how often one person or machine can call you, like "10 requests a second per IP address". Extra requests get an instant "slow down" error (HTTP 429). There are two kinds. A technical cap at the front door stops scripts and runaway retry loops. A business cap in your code says things like "at most 2 orders per phone number". | Bots, retry storms, staying under a provider's limits. | During a doorbuster sale, a reseller runs a script that hits checkout 300 times a second from one IP address. The edge limit of 10 requests a second per IP rejects 290 of them instantly, before they reach the servers. The business limit in the API, 1 per customer per deal item, stops them buying more than one even if they use many IP addresses. The same day, a buggy app version retries failed requests in a tight loop, and the limit stops it from turning a hiccup into a flood. **Why:** it protects real customers' fair share, and it protects the servers. | "Per IP at the edge, and 2 orders per phone in the API." | **WAF** (web application firewall): a filter in front of your site that blocks known attacks and bots. **DDoS protection:** absorbing floods of junk traffic. Both usually come with the CDN; mention them, don't design them. |
| 13 | Waiting room | A "you're in line" page. When far more people arrive than you can serve, they wait on a lightweight page and are let into the real site at a fixed rate, say 200 a second. Everything behind it only sees traffic it can handle. You buy it from a vendor (Cloudflare, Queue-it); you don't build it. | Demand far above capacity, or a sale that starts at an exact minute. | An electronics shop's sale starts at exactly 6:00 AM. 40,000 people are refreshing at 5:59, and the checkout was tested for 300 people a second. At 6:00, everyone lands on a "You're in line" page run by the vendor. It shuffles everyone who arrived before 6:00, then lets them in 300 a second, showing each person their place in line. **Why:** without it, 40,000 simultaneous requests would overwhelm the site, and whoever had the fastest connection would win. With it, the site runs at a load it was tested for, and the order is fair. | "Behind a flag. On only if traffic beats the plan." | **Fairness:** shuffle everyone who arrived before the start time, so the fastest clicker doesn't automatically win. |
| 14 | Replicas and failover | The main database (the primary) handles every write. Replicas are live copies that trail it by a fraction of a second, and they can answer read-only queries to share the load. One copy waits on standby. If the primary dies, the cloud promotes the standby to be the new primary in about 30 to 60 seconds; that's failover. Writes fail during that window, so the app retries. | More read capacity, and surviving a database crash. | A shop's sales dashboard runs heavy queries, like "sales by hour this month", that slow down checkout. Pointing the dashboard at a read replica moves that work off the primary, so checkout stays fast. Then, at 2 AM, the machine hosting the primary fails. The cloud notices, promotes the standby in another data center, and points the database address at it within about a minute. A few orders in that minute fail, and the app retries them. **Why:** replicas take reading pressure off the one database that handles writes, and the standby turns a hardware failure into a one-minute blip instead of hours of downtime. | "Never read stock you're about to sell from a replica. It can be a moment behind." | **Multi-AZ:** keep the standby in a different data center in the same region; cheap, always do it. **Multi-region:** a full copy in another part of the world; expensive, only if an hour's outage is unacceptable. **Point-in-time restore:** rewind the database to any minute in the last few days, to undo a bad delete. **RPO:** how much recent data you could lose. **RTO:** how long you'd be down. |
| 15 | Connection pooler | Every server copy opens connections to the database, and Postgres handles only a few hundred at once. Scale from 2 copies to 40, with 20 connections each, and that's 800: the database refuses or slows to a crawl. A pooler (PgBouncer is the classic) sits in between and shares a small set of real connections among all the servers, like a few phone lines shared by a whole office. | As soon as you add more server copies. | Before the game, the pizza shop scales from 2 API copies to 20. Each copy opens 20 database connections: 400 in total. The Postgres plan allows 200. Copies 11 to 20 can't connect, and every request they get fails, right as kickoff traffic arrives. With a pooler in between, all 20 copies connect to the pooler, which keeps 50 real connections to Postgres and lends them out for the few milliseconds each query takes. **Why:** database connections are scarce, and scaling out the API multiplies them unless something shares them. | "Postgres allows a few hundred connections. Without a pooler, scaling the API takes down the database." | Keep each transaction short. Never wait on a slow outside call, like Stripe, in the middle of one. |
| 16 | Pre-scaling | Start extra server copies and upgrade the database before a spike you know is coming. Autoscaling (the cloud adding copies when servers get busy) takes 1 to 5 minutes to react, but a promo spike hits in seconds. Without pre-scaling, you're overloaded before help arrives. | Every planned event: game day, a sale, a TV mention. | The tire shop knows the snow forecast airs on the 6 PM news on Tuesday. At 5 PM, the engineer raises the API from 2 copies to 6, moves the database to a bigger plan, and confirms the CDN has the site cached. At 6:05, traffic jumps 20x in two minutes, and the system is already sized for it. Autoscaling alone would have noticed the busy servers around 6:06 and had new copies ready around 6:09: four minutes of slow pages and errors at the worst moment. **Why:** you know when the spike is coming, so use that. | "Autoscaling reacts in minutes. The spike arrives in seconds." | Keep autoscaling on as a safety net for surprises. For workers, add copies based on how long the queue is, not on how busy the CPU is. |

## Call third parties safely

| # | Part | In plain English | Use it for | Example | Say this | Also covers |
|---|---|---|---|---|---|---|
| 17 | Hosted checkout + webhooks | Instead of building your own credit-card form, you send the customer to the payment provider's page (Stripe Checkout). They type their card there, so card numbers never touch your servers, which avoids most of the security compliance work (called PCI). When the payment succeeds, Stripe calls a URL on your server to tell you. That call is a webhook. | Every payment. | The pizza shop creates a Stripe Checkout session for order 42 ($24) and sends the customer to Stripe's page, where they pay with Apple Pay. Stripe then calls the shop's /webhooks/stripe URL: "payment completed for order 42". The shop checks the signature, saves the event id, marks order 42 paid, puts it on the kitchen screen, and replies "OK" within milliseconds. An hour later Stripe sends the same event again, which it sometimes does; the shop recognizes the event id and ignores it. **Why:** the shop never handles card numbers, which avoids heavy security audits, and the webhook is how it learns about a payment that happened on someone else's page. | "Card data never touches our servers, which shrinks our PCI scope." | **Handling webhooks:** check the signature (proof it's really Stripe), reply "OK" fast and do the work later, ignore duplicates, expect some to arrive late. Use Stripe's test mode in load tests. Stripe allows about 100 requests a second by default; ask for more before launch. SMS and email providers work the same way: call them from a worker and respect their limits. |
| 18 | Timeouts, retries, circuit breaker | Three rules for calling anything outside your system. Timeout: give up after N seconds instead of waiting forever. Retry: try again, waiting longer each time (100 ms, then 200, then 400), with a little randomness so thousands of clients don't all retry at once. Circuit breaker: after several failures in a row, stop calling for 30 seconds and fail fast, which protects you and the struggling provider. Then test with one call before resuming. | Stripe, SMS, any outside service. | On game day, Stripe slows down: calls that usually take 300 ms now take 8 seconds. Without timeouts, each checkout ties up a server for 8 seconds; soon every server is waiting on Stripe, and even the menu stops loading. With a 2-second timeout, those calls fail fast and retry once after a short wait, with the same idempotency key so nobody is charged twice. After 5 failures in a row, the circuit breaker opens: for 30 seconds, checkout immediately shows "Payments are slow, try again in a minute" instead of piling up. The rest of the site stays fast. **Why:** one slow outside service shouldn't take down everything else. | "Retries are safe only because the call carries an idempotency key." Retrying a payment without one could charge twice. | **Jitter:** the randomness in retry timing. **Bulkhead:** separate pools of connections for each outside service, so a slow Stripe can't tie up everything checkout needs. Named after a ship's watertight compartments. |

## Go-live

| # | Part | In plain English | Use it for | Example | Say this | Also covers |
|---|---|---|---|---|---|---|
| 19 | Flags and kill switches | Settings you can flip while the site is running, with no code release. A feature flag turns a feature on or off ("waiting room: on"). A kill switch is an emergency flag ("pause new orders" if payments break). You set them up in advance and test each one. | Pause orders, turn on the waiting room, hide photos to save load, close a pickup slot. | At 4:10 PM on game day, payment errors spike. The engineer flips the "pause new orders" kill switch. Within seconds, every server copy reads the flag, and the order button changes to "Online ordering is paused for a few minutes". Paid orders keep flowing to the kitchen. When payments recover at 4:25, the engineer flips it back. Later the database gets busy, so they flip "hide photos" to make every page lighter. **Why:** no code change or release in the middle of an incident. A switch takes seconds, and each one was tested the day before. | "Every switch is tested on game day." | **Graceful degradation:** turning off nice-to-haves under load so the core keeps working. **Load shedding:** rejecting some requests instantly with "try again shortly" so the rest stay fast; better than everyone timing out. |
| 20 | Load test and game day | A load test fires fake traffic at 2 to 3 times the expected peak at a copy of your system, with a written pass bar. A game day is a full rehearsal: run the load test, flip every switch, and fake a failure (say, the payment provider going down) to practice the response. | Before every launch. | Two days before a doorbuster sale, the team uses a load-testing tool (k6) to simulate 120,000 visitors in 10 minutes, including 1,000 people buying the same TV at 6:00:00. They run it against the staging copy, with Stripe in test mode. The pass bar: exactly 50 units sold per deal, no double charges, checkout p95 under 800 ms. The first run fails: p95 is 3 seconds because a query was missing an index. They fix it, rerun, and pass. On game day Thursday they run it again, flip the waiting room on and off, and make the payment test return errors to time how fast on-call notices and pauses orders. **Why:** you find the missing index on Tuesday, not at 6 AM on Friday. | "Pass means 0 oversold, 0 double charges, and p95 under 500 ms." | **Staging:** the test copy of your system. **Chaos testing:** breaking parts on purpose; a game day is the small-team version. **Capacity planning:** your Clarify math written down, from peak traffic to number of servers. |
| 21 | Safe deploys | How you release new code without breaking the event. Canary: give the new version to 1 to 5% of users first and watch for errors before everyone gets it (like the canary in a coal mine). Rollback: a tested, one-step way back to the previous version. Code freeze: no releases at all for a window around the event. | Any release near the event. | On Wednesday before the snowy weekend, the tire shop ships a bug fix. It goes to 5% of traffic first. The dashboard shows booking errors on that 5% jump from 0.1% to 4%, so they roll back with one click: only 5% of visitors saw errors, for 10 minutes. They fix the real problem, ship it properly Thursday morning, and then freeze: no releases from Thursday evening to Monday. **Why:** most outages come from changes. A canary limits who's affected, a rollback limits how long, and a freeze removes the risk during the event. | "Nothing ships during the window." | **Rolling deploy:** the usual default, replacing server copies a few at a time; it can kill work in progress unless servers finish their current job before stopping. **Blue-green:** run the new version next to the old one, switch all traffic at once, and switch back instantly if it breaks. |
| 22 | Dashboards and alerts | Live charts of how the system is doing, plus automatic pages to the on-call person when a number crosses a line. Watch four technical numbers, the "golden signals": how slow (latency), how busy (traffic), how many errors, and how full (CPU, database connections). Add business numbers: orders a minute, held vs paid, stock left. | Launch day, and every day after. | On game day, the pizza shop's dashboard shows orders per minute, p95 latency, error rate, held vs paid, slots left, Stripe errors and database connections. At 3:40, "held" keeps climbing but "paid" goes flat: customers reach Stripe, but payments aren't completing. An alert ("held minus paid above 50 for 3 minutes") pages the on-call engineer. Their runbook says: check Stripe's status page, and if Stripe is down, flip "pause orders". Errors and latency looked normal the whole time; only the business number caught it. **Why:** you can't fix what you can't see, and the right number tells on-call what is wrong, not just that something is. | "If errors pass 2% for 2 minutes, I turn on the waiting room." | **p95 latency:** 95% of requests are faster than this; it shows the slow tail an average hides. **Runbook:** a written "if this alert fires, do this", with an owner for each alert. **Logs and traces:** event records, and one request followed step by step, for debugging. **SLO:** your reliability target, like "99.9% of checkouts succeed in under 1 s". |
| 23 | Security basics | Five things to say in one breath. Encrypt traffic (HTTPS). Keep passwords and API keys in a secrets vault, not in code. Let the payment provider handle cards. Give each part of the system only the permissions it needs. Store as little personal data as possible. | When asked. | The interviewer asks, "What about security?" A good 20-second answer for the pizza shop: "Everything is HTTPS. The Stripe key and database password live in a secrets manager and are loaded at startup, never written in the code. Card numbers never reach us, because of hosted checkout. The worker that sends texts can read the queue but can't touch the database. And we store only a name and phone number for pickup." **Why:** it shows you know the basics without spending 10 minutes on them. | "HTTPS everywhere, secrets in a vault, no card data on our servers, and each service gets only what it needs." | **Authentication:** proving who you are (logging in). **Authorization:** what you're allowed to do. **Least privilege:** the "only what it needs" rule. |

## Put together: the pizza shop

```flow
Browser
CDN: site, photos, menu JSON for 30 s
WAF and rate limits: per IP, 2 orders per phone
Load balancer
API: 2 copies, more added before the game
Redis cache: slots, 2 s | Postgres: menu, slots, orders | Stripe checkout: webhooks, idempotency keys
Queue + worker: texts and emails | Sweeper job: expired holds, checks Stripe first
```

Behind flags: a waiting room (off by default), pause orders, hide photos, close a slot.

## Numbers to know

| Fact | Value |
|---|---|
| 1M events a day | about 12 a second on average; the busiest hour is 2 to 3x that |
| One row | about 1 KB, so 1M rows is about 1 GB: "it all fits in memory" |
| One Postgres database | thousands of simple writes a second |
| Postgres connections | a few hundred at most, so use a pooler (card 15) |
| Redis, one server | about 100,000 reads or writes a second, each under 1 ms |
| One API copy | hundreds to a couple of thousand requests a second |
| Autoscaling | reacts in 1 to 5 minutes |
