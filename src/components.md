# The 23 components you need

**TLDR.** Learn these 23 well and you can design any small-business-plus-spike prompt. They're in the order you use them in the interview. Each card starts with a plain-English explanation. "Also covers" defines the related terms an interviewer might use. Everything else is in the [optional reference](reference.html); skip it for now.

**Study plan**

- **Day 1:** cards 1 to 10. Then draw the pizza-shop V1 from memory.
- **Day 2:** cards 11 to 18. Then answer 2 sample questions out loud.
- **Day 3:** cards 19 to 23 and the numbers. Then 2 more questions and 10 drills.

## Draw these in V1

| # | Part | In plain English | Use it for | Say this | Also covers |
|---|---|---|---|---|---|
| 1 | CDN | A network of servers around the world that keep copies of your website's files: pages, images, scripts. Visitors get the files from a server near them instead of from yours. Think of local warehouses stocking your product, so not every order ships from the factory. | Every design. During a spike it soaks up most of the traffic, because most requests are for files that rarely change. | "The CDN takes most of the read spike before it reaches us." | **DNS:** the internet's phone book, turning pizza.com into a server address. Before a launch, set it to refresh often (a low TTL) so you can redirect traffic quickly. |
| 2 | Load balancer | A traffic cop in front of your servers. You run two or more identical copies of your backend, and it hands each request to one of them. It checks every few seconds that each copy is alive and stops sending traffic to any that don't answer. | Every design. If one copy crashes, users don't notice. | "Two copies behind a load balancer, so one can die." | **Health check:** that "are you alive?" ping. The load balancer also handles HTTPS encryption. A **reverse proxy** is the same idea. |
| 3 | Stateless API, one service | "Stateless" means a server copy doesn't remember anything about a user between requests. Anything that must be remembered (carts, orders, logins) goes in the database or cache. So any copy can handle your next request, and you get more capacity by starting more copies. If copy A kept your cart in its own memory instead, you'd be stuck with A, and your cart would vanish if A crashed. | Every design. | "One service, run as several identical copies. They're stateless, so I scale by adding copies." | **Monolith:** one program deployed as a unit, right for a small team. **Microservices:** many small programs calling each other over the network; more moving parts, for big orgs. **Managed containers:** you hand the cloud your packaged app and it runs the copies (Cloud Run, Container Apps, ECS). **Kubernetes:** running your own cluster for that; powerful, but it needs people to operate it. **Serverless functions:** code that runs once per event; fine for small glue. |
| 4 | Postgres (managed) | The standard relational database: tables of rows, like spreadsheets that many people can edit at once without corrupting anything. It's your source of truth: if it says an order is paid, it's paid. Two features matter most. Transactions: several changes succeed or fail together. Constraints: rules the database enforces itself, like "no two orders with the same id". "Managed" means the cloud handles backups, patches and recovery. | Orders, payments, stock, bookings: anything that must be correct. | "Postgres, not DynamoDB: my write changes two rows together, and at these numbers one database is plenty." | **ACID transaction:** "reserve the pizza" and "create the order" either both happen or neither does. **Index:** a sorted lookup, like a book's index, so a query finds a row without reading every row; every frequent query needs one. **DynamoDB:** Amazon's database built for huge scale on simple "get by id" lookups, but multi-row changes are clunkier, and one very popular item tops out around 1,000 writes/s. **Sharding:** splitting data across several databases; only when one can't keep up, never in V1. |
| 5 | Object storage | Cloud storage for files (photos, PDFs, videos), each saved under a name. Like Google Drive for your app: cheap and practically unlimited. Databases are bad at holding big files, so you keep the file here and just its name in the database. | Anything bigger than a row of data. | "The browser uploads straight to storage with a signed URL, so photos never pass through our servers." | **Signed URL:** a temporary link that lets one user upload or download one file directly. Serve the files through the CDN. |
| 6 | Queue + workers | A to-do list for slow work. Say a customer orders: instead of making them wait while you send a confirmation text, the server writes a note ("text this number") on the queue and replies right away. Background programs called workers pick notes off the list and do the work. In a spike, notes just wait their turn; nothing is lost. | Emails, texts, image processing: anything that can lag a bit. | "At-least-once delivery, plus workers that are safe to run twice." The queue may occasionally hand out the same note twice, so doing a job twice must be harmless. | **Dead-letter queue:** where a note goes after failing N times, so one bad job doesn't block the rest; alert on it. Add workers when the list gets long. **Kafka:** an event log many programs can read and re-read; overkill for a to-do list. **Pub/sub:** one message delivered to several listeners. **Outbox:** save the message in the same transaction as the order, so you can't save one and lose the other. |
| 7 | Sweeper and reconciliation jobs | Small programs that run on a timer (every minute, every night) to clean up. A sweeper finds things that got stuck, like a pizza someone reserved but never paid for, and releases them. A reconciliation job compares your records with an outside source, like Stripe's list of payments, and fixes mismatches. They catch whatever slipped through: crashed requests, lost messages. | Expired holds, stuck orders, matching payments. | "Every minute, release expired holds, after asking Stripe whether they were paid." | **Cron:** the classic name for "run this on a schedule". Make sure only one copy runs at a time, so two sweepers don't fight. |

## Protect the invariants

An invariant is a rule that must never break, like "never sell more pizzas than the ovens can make".

| # | Part | In plain English | Use it for | Say this | Also covers |
|---|---|---|---|---|---|
| 8 | Conditional update | Do the check and the change as one database command: "subtract 2 from stock, but only if at least 2 are left". The database runs it as a single step, so two buyers can't both see "1 left" and both buy it. If nothing changed, it's sold out. The bug it prevents: code that reads "1 left", then writes "0 left" a moment later; two customers can slip in between those steps and both succeed. | **No oversell** of stock, seats or time slots. | "One statement, so the database refuses to go below zero." The SQL: `UPDATE stock SET left = left - 2 WHERE id = ? AND left >= 2`. | **SELECT ... FOR UPDATE:** lock the row while you run more complicated logic; others wait their turn. Avoid keeping the count in Redis or using a "distributed lock": then two places hold the truth, and they can disagree. |
| 9 | Holds that expire | Like a store setting an item aside for 10 minutes while you get your wallet. When checkout starts, you reserve the item first (a hold), then take payment. If they pay, the hold becomes a sale. If 10 minutes pass without payment, the sweeper (card 7) puts it back on sale. Each order's status only moves forward: held, then paid or expired. | Anything reserved before it's paid for. | "Hold, then charge, so we never take money for something we can't deliver." | **State machine:** the fixed list of statuses and the allowed moves between them. Because status only moves forward, a late or repeated message from Stripe can't turn a paid order back into a held one. |
| 10 | Idempotency key | "Idempotent" means doing something twice has the same effect as doing it once. Networks are flaky: a customer double-taps "Pay", or their phone retries after a timeout. So the app attaches a random id to each user action, one per tap of "Place order". The server saves it with a rule that ids must be unique. If the same id arrives again, the server returns the original result instead of creating a second order. | **No double charge.** Every action that creates or charges something, and every webhook. | "A client key with a unique constraint, the same key passed to Stripe, and webhook event ids deduped." | **Unique constraint:** the database rule that rejects duplicates. The same trick stops double booking: one booking per bay per time slot. **Webhook dedupe:** Stripe can send the same notice twice, so save its event id and ignore repeats. True "exactly once" isn't achievable; you get "at least once, and repeats are harmless". |

## Survive the spike

| # | Part | In plain English | Use it for | Say this | Also covers |
|---|---|---|---|---|---|
| 11 | Cache with a short TTL | A cache is a small, very fast memory holding copies of recent answers, so you don't ask the database every time. Redis is the usual tool. The TTL ("time to live") is how long a copy is kept before it's thrown away and fetched again. With a 2-second TTL, an answer is at most 2 seconds old, and the database sees one query every 2 seconds instead of thousands. | Things everyone reads at once: "slots left", the menu. | "Cached for 2 s. It's a hint; the database is the truth." Never decide a sale from the cache; the conditional update (card 8) decides. | **Invalidation:** deleting copies whenever the data changes; harder than a short TTL. **Stampede:** a popular copy expires and thousands of requests hit the database at once; let one request refresh it while the others get the slightly old copy. **Hot key:** one item everyone reads; also keep a 1-second copy inside each server. |
| 12 | Rate limits | A cap on how often one person or machine can call you, like "10 requests a second per IP address". Extra requests get an instant "slow down" error (HTTP 429). There are two kinds. A technical cap at the front door stops scripts and runaway retry loops. A business cap in your code says things like "at most 2 orders per phone number". | Bots, retry storms, staying under a provider's limits. | "Per IP at the edge, and 2 orders per phone in the API." | **WAF** (web application firewall): a filter in front of your site that blocks known attacks and bots. **DDoS protection:** absorbing floods of junk traffic. Both usually come with the CDN; mention them, don't design them. |
| 13 | Waiting room | A "you're in line" page. When far more people arrive than you can serve, they wait on a lightweight page and are let into the real site at a fixed rate, say 200 a second. Everything behind it only sees traffic it can handle. You buy it from a vendor (Cloudflare, Queue-it); you don't build it. | Demand far above capacity, or a sale that starts at an exact minute. | "Behind a flag. On only if traffic beats the plan." | **Fairness:** shuffle everyone who arrived before the start time, so the fastest clicker doesn't automatically win. |
| 14 | Replicas and failover | The main database (the primary) handles every write. Replicas are live copies that trail it by a fraction of a second, and they can answer read-only queries to share the load. One copy waits on standby. If the primary dies, the cloud promotes the standby to be the new primary in about 30 to 60 seconds; that's failover. Writes fail during that window, so the app retries. | More read capacity, and surviving a database crash. | "Never read stock you're about to sell from a replica. It can be a moment behind." | **Multi-AZ:** keep the standby in a different data center in the same region; cheap, always do it. **Multi-region:** a full copy in another part of the world; expensive, only if an hour's outage is unacceptable. **Point-in-time restore:** rewind the database to any minute in the last few days, to undo a bad delete. **RPO:** how much recent data you could lose. **RTO:** how long you'd be down. |
| 15 | Connection pooler | Every server copy opens connections to the database, and Postgres handles only a few hundred at once. Scale from 2 copies to 40, with 20 connections each, and that's 800: the database refuses or slows to a crawl. A pooler (PgBouncer is the classic) sits in between and shares a small set of real connections among all the servers, like a few phone lines shared by a whole office. | As soon as you add more server copies. | "Postgres allows a few hundred connections. Without a pooler, scaling the API takes down the database." | Keep each transaction short. Never wait on a slow outside call, like Stripe, in the middle of one. |
| 16 | Pre-scaling | Start extra server copies and upgrade the database before a spike you know is coming. Autoscaling (the cloud adding copies when servers get busy) takes 1 to 5 minutes to react, but a promo spike hits in seconds. Without pre-scaling, you're overloaded before help arrives. | Every planned event: game day, a sale, a TV mention. | "Autoscaling reacts in minutes. The spike arrives in seconds." | Keep autoscaling on as a safety net for surprises. For workers, add copies based on how long the queue is, not on how busy the CPU is. |

## Call third parties safely

| # | Part | In plain English | Use it for | Say this | Also covers |
|---|---|---|---|---|---|
| 17 | Hosted checkout + webhooks | Instead of building your own credit-card form, you send the customer to the payment provider's page (Stripe Checkout). They type their card there, so card numbers never touch your servers, which avoids most of the security compliance work (called PCI). When the payment succeeds, Stripe calls a URL on your server to tell you. That call is a webhook. | Every payment. | "Card data never touches our servers, which shrinks our PCI scope." | **Handling webhooks:** check the signature (proof it's really Stripe), reply "OK" fast and do the work later, ignore duplicates, expect some to arrive late. Use Stripe's test mode in load tests. Stripe allows about 100 requests a second by default; ask for more before launch. SMS and email providers work the same way: call them from a worker and respect their limits. |
| 18 | Timeouts, retries, circuit breaker | Three rules for calling anything outside your system. Timeout: give up after N seconds instead of waiting forever. Retry: try again, waiting longer each time (100 ms, then 200, then 400), with a little randomness so thousands of clients don't all retry at once. Circuit breaker: after several failures in a row, stop calling for 30 seconds and fail fast, which protects you and the struggling provider. Then test with one call before resuming. | Stripe, SMS, any outside service. | "Retries are safe only because the call carries an idempotency key." Retrying a payment without one could charge twice. | **Jitter:** the randomness in retry timing. **Bulkhead:** separate pools of connections for each outside service, so a slow Stripe can't tie up everything checkout needs. Named after a ship's watertight compartments. |

## Go-live

| # | Part | In plain English | Use it for | Say this | Also covers |
|---|---|---|---|---|---|
| 19 | Flags and kill switches | Settings you can flip while the site is running, with no code release. A feature flag turns a feature on or off ("waiting room: on"). A kill switch is an emergency flag ("pause new orders" if payments break). You set them up in advance and test each one. | Pause orders, turn on the waiting room, hide photos to save load, close a pickup slot. | "Every switch is tested on game day." | **Graceful degradation:** turning off nice-to-haves under load so the core keeps working. **Load shedding:** rejecting some requests instantly with "try again shortly" so the rest stay fast; better than everyone timing out. |
| 20 | Load test and game day | A load test fires fake traffic at 2 to 3 times the expected peak at a copy of your system, with a written pass bar. A game day is a full rehearsal: run the load test, flip every switch, and fake a failure (say, the payment provider going down) to practice the response. | Before every launch. | "Pass means 0 oversold, 0 double charges, and p95 under 500 ms." | **Staging:** the test copy of your system. **Chaos testing:** breaking parts on purpose; a game day is the small-team version. **Capacity planning:** your Clarify math written down, from peak traffic to number of servers. |
| 21 | Safe deploys | How you release new code without breaking the event. Canary: give the new version to 1 to 5% of users first and watch for errors before everyone gets it (like the canary in a coal mine). Rollback: a tested, one-step way back to the previous version. Code freeze: no releases at all for a window around the event. | Any release near the event. | "Nothing ships during the window." | **Rolling deploy:** the usual default, replacing server copies a few at a time; it can kill work in progress unless servers finish their current job before stopping. **Blue-green:** run the new version next to the old one, switch all traffic at once, and switch back instantly if it breaks. |
| 22 | Dashboards and alerts | Live charts of how the system is doing, plus automatic pages to the on-call person when a number crosses a line. Watch four technical numbers, the "golden signals": how slow (latency), how busy (traffic), how many errors, and how full (CPU, database connections). Add business numbers: orders a minute, held vs paid, stock left. | Launch day, and every day after. | "If errors pass 2% for 2 minutes, I turn on the waiting room." | **p95 latency:** 95% of requests are faster than this; it shows the slow tail an average hides. **Runbook:** a written "if this alert fires, do this", with an owner for each alert. **Logs and traces:** event records, and one request followed step by step, for debugging. **SLO:** your reliability target, like "99.9% of checkouts succeed in under 1 s". |
| 23 | Security basics | Five things to say in one breath. Encrypt traffic (HTTPS). Keep passwords and API keys in a secrets vault, not in code. Let the payment provider handle cards. Give each part of the system only the permissions it needs. Store as little personal data as possible. | When asked. | "HTTPS everywhere, secrets in a vault, no card data on our servers, and each service gets only what it needs." | **Authentication:** proving who you are (logging in). **Authorization:** what you're allowed to do. **Least privilege:** the "only what it needs" rule. |

## Put together: the pizza shop

```flow
Browser
CDN: site, photos, menu JSON for 30 s
WAF and rate limits: per IP, 2 orders per phone
Load balancer
API: 2 copies, more added before the game
Redis cache: slots, 2 s | Postgres: menu, slots, orders | Stripe checkout: webhooks, idempotency keys
Queue + worker: texts and emails | Sweeper job: expired holds, checks Stripe first
```

Behind flags: a waiting room (off by default), pause orders, hide photos, close a slot.

## Numbers to know

| Fact | Value |
|---|---|
| 1M events a day | about 12 a second on average; the busiest hour is 2 to 3x that |
| One row | about 1 KB, so 1M rows is about 1 GB: "it all fits in memory" |
| One Postgres database | thousands of simple writes a second |
| Postgres connections | a few hundred at most, so use a pooler (card 15) |
| Redis, one server | about 100,000 reads or writes a second, each under 1 ms |
| One API copy | hundreds to a couple of thousand requests a second |
| Autoscaling | reacts in 1 to 5 minutes |
| A payment call | 200 ms to over 1 s; Stripe allows about 100 requests a second by default |
